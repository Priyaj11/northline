## TC-SEC-001 Account data requires authentication

**Requirement** REQ-SEC-001  
**Technique** Negative Testing  
**Layer** security  
**Priority** Critical  
**Automation** planned  
**Introduced in phase** 5

**Preconditions** A customer identifier is known. No session is established.

**Test data** GET /services/bank/customers/{customerId}/accounts with no credentials

**Steps**

1. Request the customer's accounts with no credentials, cookie or token.
2. Record the status and whether financial data is returned.

**Expected result** Access is refused. Phase 1 observed full account data being returned with no credentials, so this case is expected to fail. If it does, it is recorded as a defect with evidence in Phase 6, and no exploitation beyond this single request is performed.

## TC-SEC-003 A customer cannot read another customer's account

**Requirement** REQ-SEC-002  
**Technique** Negative Testing  
**Layer** security  
**Priority** Critical  
**Automation** planned  
**Introduced in phase** 5

**Preconditions** Two customers exist, each owning at least one account.

**Test data** customer A's session requesting customer B's account identifier

**Steps**

1. Register a second customer and note one of their account identifiers.
2. Log in as the first customer.
3. Request the second customer's account within the first customer's session.

**Expected result** Access is refused. This is Broken Object Level Authorisation, where an application checks that you are logged in but not that the record belongs to you.

## TC-SEC-004 A customer cannot transfer from another customer's account

**Requirement** REQ-SEC-002  
**Technique** Negative Testing  
**Layer** security  
**Priority** Critical  
**Automation** planned  
**Introduced in phase** 5

**Preconditions** Two customers exist with accounts.

**Test data** customer A's session, source account belonging to customer B

**Steps**

1. Log in as the first customer.
2. Attempt a transfer whose source is the second customer's account.
3. Read the second customer's balance afterwards.

**Expected result** The transfer is refused and the balance is unchanged. This is the highest severity failure the application could have.

## TC-SEC-005 Credentials are not transmitted in the URL path

**Requirement** REQ-SEC-003  
**Technique** Negative Testing  
**Layer** security  
**Priority** High  
**Automation** planned  
**Introduced in phase** 5

**Preconditions** The service interface is reachable.

**Test data** the login endpoint signature discovered in Phase 1

**Steps**

1. Inspect the login endpoint's declared shape in the service description.
2. Determine whether the password appears as a path segment.

**Expected result** Credentials are carried in a request body or header, not the path. Phase 1 observed a login endpoint taking both as path segments, so this case is expected to fail. URLs appear in access logs, browser history and proxy logs, none of which are treated as secret stores.

## TC-SEC-007 Behaviour of a session after the browser session ends

**Requirement** REQ-SEC-004  
**Technique** State Transition Testing  
**Layer** security  
**Priority** High  
**Automation** planned  
**Introduced in phase** 5

**Preconditions** A customer has logged in.

**Test data** the session cookie issued at login

**Steps**

1. Log in and record the session cookie attributes.
2. Discard the cookie and request an authenticated page.

**Expected result** Access is refused without the cookie. The cookie's attributes are recorded as evidence, since ParaBank has no server-side session timeout endpoint and timeout cannot be tested through the service interface.

## TC-SEC-008 Input validation on the transfer amount is enforced server side

**Requirement** REQ-SEC-004  
**Technique** Negative Testing  
**Layer** security  
**Priority** Critical  
**Automation** planned  
**Introduced in phase** 5

**Preconditions** Two valid accounts are known.

**Test data** a negative amount sent directly to the service, bypassing the browser form

**Steps**

1. Send a transfer request with a negative amount directly to the service.
2. Read both balances afterwards.

**Expected result** The request is refused. Client-side validation is a convenience for users, not a control. Any rule enforced only in the browser is not enforced at all, because the service can be called directly.
