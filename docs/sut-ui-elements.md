# Selector strategy and findings

Recorded from this file's generated content, before any page object was written.

## Finding 1: a randomly generated element identifier

On billpay.htm the payee phone number field carries an identifier that looks
generated rather than authored:

    <input type="text" name="payee.phoneNumber"
           id="2a8429d9-d991-45ba-86de-cfa92c4581b9">

If that value regenerates on each page load, any selector written against it
breaks on the next run. Northline selects that field by its name attribute
instead. Verify by reloading the page and comparing.

## Finding 2: a field named "input"

The transfer amount field is name="input" id="amount". A name carrying no
meaning is a maintenance hazard, so Northline selects it by #amount.

## Finding 3: form controls with no name attribute

The transfer page's account dropdowns have id="fromAccountId" and
id="toAccountId" but no name attribute. A control without a name is not
included in a normal form submission, which suggests the page depends on
scripting to send those values.

## Finding 4: four submit buttons with identical text

findtrans.htm has four submit controls all reading "Find Transactions",
separated only by id: findById, findByDate, findByDateRange, findByAmount.
Selecting by visible text is ambiguous here, so identifiers are used.

## Finding 5: form inputs cannot be labelled

The login inputs carry no id attribute, so no <label for="..."> can be
associated with them programmatically. Playwright's preferred locator,
get_by_label, is therefore unusable on this page.

This is not a limitation of the tooling. It is the accessibility defect that
TC-ACC-004 (REQ-ACC-002) exists to find, and a screen reader user faces exactly
the same problem the automation does: nothing in the markup says what the field
is for. Confirmed with axe-core in Phase 5.

## Selector precedence used by Northline

  1. A stable id, where one exists and is clearly authored (#amount, #findById)
  2. A name attribute (input[name='username'], input[name='payee.name'])
  3. A submit control's value (input[type='submit'][value='Log In'])
  4. Never a generated id, a class used for styling, or a text string that
     appears more than once on the page

## Finding 6: dropdown options are never "visible"

Not an application defect. A framework lesson worth recording.

The first run of the transfer suite timed out after ten seconds on:

    page.wait_for_selector("#fromAccountId option")

The Playwright log showed the locator resolving to 11 elements and then waiting
for them to become visible. An <option> inside a <select> is never visible in
the layout sense, because the browser renders the dropdown control rather than
the options, so the default state="visible" can never be satisfied.

Two corrections, both applied in pages/transfer_page.py:

  1. Wait with state="attached" rather than the default state="visible".
  2. Read option values with evaluate_all reading the value attribute, rather
     than all_inner_texts. inner_text depends on layout and returns nothing for
     elements the browser never renders.

The general rule: "present in the document" and "visible on screen" are
different conditions, and choosing the wrong one produces a timeout that looks
like a slow application and is not.

## Finding 7: the login page renders today's date

The Latest News panel on index.htm contains <li class="captionthree"> holding
the current date. Without handling, a visual baseline of that page would fail
every day at midnight for a reason unrelated to layout.

Northline masks that element rather than taking either of the alternatives.
Cropping to a smaller region would lose coverage of the header, footer and
overall layout, which is most of what the test is for. Raising the tolerance
until the date fits underneath it would hide a real change of the same size
anywhere else on the page.

The general rule: never snapshot a page whose content is data-driven, and where
a page has one changing region, mask that region rather than loosening the
comparison.
