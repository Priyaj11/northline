# DEF-007  A transfer with sub-cent precision makes accounts permanently unreadable

Status:          Open
Severity:        Critical
Priority:        P1
Requirement:     REQ-XFER-004, REQ-ACCT-001, REQ-ACCT-002
Test cases:      TC-XFER-010
Detected in:     Phase 7C-PRE, transfer validation suite
Detected by:     tests/api/test_transfer_validation_api.py
Reproducibility: Consistent, every attempt

## Environment

  System Under Test: ParaBank, image parasoft/parabank
  Environment:       local
  Detected:          2026-08-31

## Summary

The application accepts a transfer amount carrying more than two decimal places,
stores the resulting balance at that precision, and is then unable to read the
affected accounts back. Every subsequent request for those accounts returns
HTTP 500.

The application writes a value it cannot read.

## Steps to reproduce

From a freshly reset environment:

    B="http://localhost:8080/parabank/services/bank"
    curl -s -o /dev/null -w "%{http_code}\n" -H "Accept: application/json" \
      "$B/customers/12212/accounts"
    curl -s -X POST "$B/transfer?fromAccountId=12345&toAccountId=12456&amount=10.005"
    curl -s -o /dev/null -w "%{http_code}\n" -H "Accept: application/json" \
      "$B/customers/12212/accounts"

## Expected result

Either the amount is refused, or it is rounded to two decimal places on both
sides and the accounts remain readable.

## Actual result

    before                          customers/12212/accounts   200
    transfer of 10.005              200, "Successfully transferred $10.005"
    after                           customers/12212/accounts   500
                                    accounts/12345             500
                                    accounts/12456             500
                                    accounts/12567 untouched   200

## Root cause, from the application log

    Caused by: java.lang.ArithmeticException: Rounding necessary
        at java.math.BigDecimal.setScale(Unknown Source)
        at com.parasoft.parabank.dao.jdbc.JdbcAccountDao$AccountMapper.mapRow(
            JdbcAccountDao.java:29)
        at com.parasoft.parabank.dao.jdbc.JdbcAccountDao.getAccountsForCustomerId(
            JdbcAccountDao.java:121)

The row mapper calls BigDecimal.setScale without a rounding mode. That form
throws whenever the value carries more precision than the requested scale,
which is exactly what the stored balance now has.

The write path applies no such constraint, so the two halves disagree about
what a balance may contain.

## Blast radius

Both accounts in the transfer become unreadable, and so does every query that
includes them. getAccountsForCustomerId appears in the trace, so the customer's
entire account list fails, which is the first screen a customer sees after
logging in.

An account not involved in the transfer, 12567, still returns 200. The
corruption is per row, not database wide, but any list containing a corrupted
row fails as a whole.

## Recovery

Only cleanDB followed by initializeDB, which destroys all application data.
There is no path back through the interface: the account cannot be read, so it
cannot be corrected through any operation that reads it first.

In a production bank that means a customer's accounts are inaccessible until
somebody corrects the value directly in the database.

## Business impact

A single transfer with three decimal places renders a customer unable to see
any of their accounts through the application. The amount need not be large or
malicious: 10.005 is a plausible result of a currency conversion, an interest
calculation, or a percentage-based fee.

Combined with DEF-005, which records that the services require no
authentication, this is remotely triggerable by anyone who can reach the server
against any customer they choose.

Severity is Critical on availability and data integrity grounds. It does not
lose money, and that is the only reason it is not worse: the balance is still
there, nothing can read it.

## How this was found

Boundary value analysis on decimal precision. TC-XFER-010 exists because money
carries exactly two decimal places and a value with three is the boundary case,
and the test was written to establish behaviour rather than to assert an
expectation, because the behaviour was unknown.

It also caused a confusing intermediate result worth recording. Four later
tests failed with HTTP 500 on account reads, and the immediately preceding test
used scientific notation, so that looked like the cause. It was not. The
scientific notation case was collateral damage from the 10.005 transfer two
positions earlier, and the stack trace said so. Reading the trace beats blaming
the nearest preceding action.
