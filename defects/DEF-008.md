# DEF-008  The transaction date range search accepts an invalid date

Status:          Open
Severity:        Medium
Priority:        P3
Requirement:     REQ-TXN-002
Test cases:      TC-TXN-003
Detected in:     Phase 7C-PRE, browser transaction history suite
Reproducibility: Consistent

## Environment

  System Under Test: ParaBank, image parasoft/parabank
  Environment:       local
  Detected:          2026-08-31

## Summary

The find transactions page requires dates in MM-DD-YYYY. It rejects
slash-separated and ISO formats with "Invalid date format" in the matching error
element, and it ACCEPTS 31-12-2026 without any message, returning an empty
result table.

There is no month 31.

## Steps to reproduce

  1. Log in and open Find Transactions.
  2. Select an account.
  3. Enter 31-12-2026 in both date fields.
  4. Search by date range.

## Expected result

An error stating the date is not valid, as happens for the other rejected
formats.

## Actual result

No message in #dateRangeError, and an empty results table.

## What the format checking actually does

Established by experiment:

    12-01-2025  MM-DD-YYYY   accepted, correct format
    01-12-2025  DD-MM-YYYY   accepted, returns results for a different range
    12/01/2025  slashes      rejected, "Invalid date format"
    2025-12-01  ISO          rejected, "Invalid date format"

So the page validates the SHAPE of the string and not the values inside it. Any
two-digit, two-digit, four-digit sequence separated by hyphens is accepted.

## Business impact

A customer outside the United States enters dates in day-month-year order by
habit. They are not told they have done so. They are shown either an empty table
or results for a range they did not ask for, with no way to tell which.

The failure is silent in both directions, and that is what makes it worth
raising rather than the invalid date itself:

  a correct range with no matching transactions shows an empty table
  a misread range shows an empty table or the wrong transactions

Nothing distinguishes those cases for the customer. Severity is Medium because
no money is at risk and the data itself is unaffected; a customer simply cannot
trust what the search tells them.

## Handling in the test suite

tests/ui/test_billpay_ui.py marks the case as a strict expected failure
referencing this defect, so it goes red if the validation is ever fixed without
the test being updated.
