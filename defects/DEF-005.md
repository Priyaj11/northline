# DEF-005  The REST services require no authentication

Status:          Open
Severity:        Critical
Priority:        P1
Requirement:     REQ-SEC-001, REQ-SEC-002
Test cases:      TC-SEC-001, TC-SEC-002, TC-SEC-003
Detected in:     Phase 5B, security-adjacent suite
Detected by:     tests/security/test_service_authorization.py
Reproducibility: Consistent, every request

## Environment

  System Under Test: ParaBank, image parasoft/parabank
  Environment:       local
  Detected:          2026-08-31
  First observed:    2026-08-29, Phase 1 endpoint discovery

## Summary

The REST services under /parabank/services/bank return customer financial data
to any client that can reach the server. No session, no cookie, no token and no
authorisation header is required or checked.

## Steps to reproduce

    B="http://localhost:8080/parabank/services/bank"
    curl -s -H "Accept: application/json" "$B/customers/12212/accounts"
    curl -s -H "Accept: application/json" "$B/accounts/12345/transactions"

No credentials are presented in either request.

## Expected result

Access refused. A customer's accounts and transactions require an
authenticated session belonging to that customer.

## Actual result

HTTP 200 with the full data in both cases. The accounts call returns every
account belonging to customer 12212, including balances.

## Consequence: no object level authorisation either

Because there is no authentication, there is no notion of a requester, and
therefore no possibility of checking that a record belongs to them. TC-SEC-003
registered a second customer through the browser and then read one of that
customer's accounts with no credentials at all. It returned HTTP 200 with the
balance.

That is Broken Object Level Authorisation, but it is not a separate defect. It
is what the absence of authentication necessarily produces, and fixing this
defect removes it. Recording it as its own entry would triple-count one problem
and give a team no way to prioritise.

## Business impact

Any client that can reach the server can read any customer's accounts,
balances and transaction history by supplying only a customer or account
number. Both are sequential in the seeded data.

Combined with DEF-001, the impact is worse than disclosure. DEF-001 records
that the transfer endpoint does not validate the amount and moves money in
reverse for a negative value. Together, an unauthenticated client can both read
and drain any account.

The login response also carries a social security number field, so the exposed
data is not limited to financial records.

## Scope of testing performed

Three requests, one per test case. No enumeration of customer or account
identifiers was performed, no data was retained beyond the assertions, and no
attempt was made to write data through the unauthenticated path beyond the
single transfer already covered by DEF-001.

Northline verifies whether a control exists. It does not exploit its absence.

## Note

The browser channel is NOT affected. Session handling through the web interface
was tested in the same suite and behaved correctly: protected pages return no
data without a session, logging out ends access, discarding the session cookie
ends access, and the session cookie is marked HttpOnly.

The controls exist in one channel and are absent in the other. That is a common
pattern where security was applied where developers were thinking about users
and omitted where they were thinking about integrations.
