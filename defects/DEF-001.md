# DEF-001  Negative transfer amounts are accepted and move money in reverse

Status:          Open
Severity:        Critical
Priority:        P1
Requirement:     REQ-XFER-003
Test cases:      TC-XFER-005, TC-XFER-007
Detected in:     Phase 3B, API test suite
Detected by:     tests/api/test_transfer_api.py::test_invalid_amounts_do_not_move_money
Reproducibility: Consistent, 2 of 2 attempts

## Environment

  System Under Test: ParaBank, image parasoft/parabank
  Environment:       local
  Detected:          2026-08-30

## Summary

The funds transfer endpoint accepts a negative amount, returns HTTP 200 with a
success message, and moves money in the opposite direction to the one requested.
The source account is credited and the destination account is debited.

An amount of 0.00 IS correctly rejected. Only negative amounts pass. This is the
signature of a validation testing that the amount is not zero, where it should
test that the amount is greater than zero.

## Preconditions

Two accounts belonging to the same customer, with known balances.

## Steps to reproduce

  1. Read the balance of account A and account B.
  2. POST /services/bank/transfer with fromAccountId=A, toAccountId=B,
     amount=-500.00
  3. Read both balances again.

## Expected result

The request is refused. Neither balance changes.

## Actual result

HTTP 200 with the body "Successfully transferred $-500.00 from account #12345
to account #12456". Account A is credited by 500.00 and account B is debited.

## Evidence

Captured from the test run log on 2026-08-30 at 01:16.

Case A, amount -0.01, from account 12345 to account 12456

    before   12345 = -2401.02      12456 = 111.47
    response 200  "Successfully transferred $-0.01 from account #12345
                   to account #12456"
    after    12345 = -2401.01      12456 = 111.46

  The source rose by 0.01. The destination fell by 0.01.

Case B, amount -500.00, same accounts

    before   12345 = -2401.01      12456 = 111.46
    response 200  "Successfully transferred $-500.00 from account #12345
                   to account #12456"
    after    12345 = -1901.01

  The source rose by exactly 500.00. The destination reading after this
  transfer was not captured in that run, because the test asserted on the
  source first and stopped there. A clean reproduction capturing both sides
  is recorded in the section below.

Case C, amount 0.00, same accounts

    Neither balance changed. Zero is handled correctly.

## Business impact

Money can be moved out of any account by requesting a negative transfer FROM
the account to be drained. The amount is unbounded.

Combined with the Phase 1 observation that the REST services require no
authentication (REQ-SEC-001), any client that can reach the server can drain
any account without credentials. That combination raises this from a validation
defect to a total loss of funds control.

## Notes

Client-side validation in the browser form may prevent a negative amount being
entered by a user. That is irrelevant. The service can be called directly, so a
rule enforced only in the browser is not enforced. TC-SEC-008 covers this
principle specifically.

## Handling in the test suite

TC-XFER-005 and TC-XFER-007 are marked as expected failures with strict mode
enabled, referencing this defect. The suite therefore stays green for new
regressions while this known defect remains visible, and the strict flag means
the suite fails if the behaviour is ever fixed without the tests being updated.

The release gate does not read this from the test results. GATE-CRITICAL-DEFECT
reads the defect register, so an open Critical defect produces a NO-GO decision
regardless of how the tests are marked.

## Clean reproduction, captured 2026-08-30

Both sides captured in a single self-contained sequence using curl:

    B="http://localhost:8080/parabank/services/bank"
    curl -s "$B/accounts/12345"
    curl -s "$B/accounts/12456"
    curl -s -X POST "$B/transfer?fromAccountId=12345&toAccountId=12456&amount=-100.00"
    curl -s "$B/accounts/12345"
    curl -s "$B/accounts/12456"

Result:

    before    12345 = -1901.02      12456 = -388.53
    request   POST /transfer  from=12345  to=12456  amount=-100.00
    response  200  "Successfully transferred $-100.00 from account #12345
                    to account #12456"
    after     12345 = -1801.02      12456 = -488.53

The source rose by exactly 100.00. The destination fell by exactly 100.00.

The transfer is a perfect symmetric reversal: money is conserved, but the
direction is inverted. The application is not corrupting the amount, it is
applying the sign without validating it.

This also retroactively confirms the destination side of case B above. Account
12456 stood at 111.47 before the -500.00 transfer and reads -388.53 here, which
is 111.47 minus 500.00 exactly.

## Note on response format

This reproduction used curl, which sends no Accept header, and the service
answered in XML. The Python client sends Accept: application/json and receives
JSON. The endpoints content-negotiate. The defect is identical in both formats;
only the representation differs.

## Amendment, 2026-08-30: the amount is not validated at all

The original writeup stated that an amount of 0.00 was correctly rejected, and
inferred that the validation tested for a non-zero amount rather than a positive
one. Both statements were wrong. They came from a test that asserted only that
balances did not change, which a zero-amount transfer satisfies trivially.

A database-layer test performed a transfer of 0.00 and then inspected the
ledger:

    request   POST /transfer  from=12345  to=12456  amount=0.00
    response  200  "Successfully transferred $0.00 from account #12345
                    to account #12456"
    written   14920  account 12345  Debit   0.00  Funds Transfer Sent
              15031  account 12456  Credit  0.00  Funds Transfer Received

The transfer was accepted and produced records on both accounts.

### Corrected summary

ParaBank does not validate the transfer amount. Negative amounts are accepted
and move money in the opposite direction. Zero amounts are accepted and write
records carrying no value. Both return HTTP 200 with a success message.

Severity remains Critical and priority remains P1, driven by the negative
amount behaviour. The zero-amount behaviour alone would be Medium: it pollutes
the ledger and the transaction history with meaningless entries, but no money
is misplaced.

### Why the original test missed it

The API-level test asserted that no money moved. That is true of a zero-amount
transfer, so the test passed while the request was in fact accepted.

Rejection and no-monetary-effect are different claims. A test for rejection has
to assert that no RECORD was written, which requires reading the ledger rather
than the balance. This is precisely what the certification data store exists
for, and it caught the error the API layer structurally could not.

The general lesson: when a negative test passes, check that it would still fail
if the system did the wrong thing. An assertion that cannot distinguish
"refused" from "accepted with no effect" is not testing what it claims to test.

## Third piece of evidence, 2026-08-31: scientific notation

Found by TC-XFER-011 during the transfer validation work.

    request   POST /transfer  from=12345  to=12456  amount=1e3
    response  200  "Successfully transferred $1E+3 from account #12345
                    to account #12456"
    before    12345 = -2300.00      12456 = 10.45
    after     12345 = -3300.00      12456 = 1010.45

The value was parsed as 1000 and moved. The debit equals the credit, so money
is conserved, which is why this is recorded here rather than raised as a
separate defect: it is the same root cause, the amount is not validated.

The evidence for that root cause is now three behaviours:

    negative amounts       accepted, money moves in reverse
    zero amounts           accepted, empty records written
    scientific notation    accepted, parsed as a number

Note also the confirmation message. A customer performing this transfer is told
they moved "$1E+3". A currency amount rendered in scientific notation is not a
currency amount any customer will recognise.

Four other malformed values ARE handled correctly and do not move money:
letters, an empty amount, a currency symbol, and a thousands separator. The
application is not indiscriminate, it simply accepts anything Java's number
parsing accepts, which is a wider set than the set of valid currency amounts.
