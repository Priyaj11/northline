# DEF-003  Form fields have no accessible name

Status:          Open
Severity:        High
Priority:        P2
Requirement:     REQ-ACC-002
Test cases:      TC-ACC-004
Detected in:     Phase 5A, automated accessibility scan
Detected by:     tests/accessibility/test_axe_scans.py
Reproducibility: Consistent, every scan

## Environment

  System Under Test: ParaBank, image parasoft/parabank
  Environment:       local
  Tool:              axe-core 4.13.0, rule tags wcag2a wcag2aa wcag21a wcag21aa
  Browser:           Chromium
  Detected:          2026-08-31

## Summary

Form inputs and select elements across four pages have no programmatically
associated label, so assistive technology cannot announce what any field is
for. The captions are present visually but are not associated in the markup.

## Affected elements

    page           rule          elements
    -----------    -----------   --------
    login          label                2
    register       label               13
    transfer       label                1
    transfer       select-name          2
    billpay        label                9
    billpay        select-name          1
                                 --------
                   total               28

Success criteria: WCAG 2.1 4.1.2 Name, Role, Value (level A).

## Steps to reproduce

  1. npm install
  2. .venv/bin/python scripts/scan_accessibility.py
  3. Read docs/accessibility-report.md, or run:
     .venv/bin/python -m pytest -m accessibility -k accessible_name

## Expected result

Every form control has an accessible name, through a label element associated
by the for attribute, an aria-label, or an aria-labelledby reference.

## Actual result

28 controls have none. axe reports label as critical impact and select-name as
critical impact.

## Business impact

A customer using a screen reader cannot complete a transfer or a bill payment,
because nothing in the markup says which field is the amount and which is the
destination account. The visual caption is invisible to the software they rely
on.

WCAG 2.1 level AA is the standard named in REQ-ACC-001. In Ontario it is also
the level referenced by the Accessibility for Ontarians with Disabilities Act
for public-facing web content, which makes this a compliance matter and not
only a usability one.

## Note on how this was found

Predicted from the markup in Phase 3C, before the accessibility phase began.
docs/sut-ui-elements.md Finding 5 recorded that the login inputs carry no id
attribute, so no label could reference them, and that this was why Playwright's
get_by_label locator was unusable on that page.

The automation and the screen reader hit the same wall for the same reason.
Where a test framework cannot find an element by its label, a person using
assistive technology usually cannot either.
